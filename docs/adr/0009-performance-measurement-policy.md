# ADR 0009: Bytes are gated, timings are reported, and neither is a score

**Status:** accepted

## Context

P3-02 asks for "measured performance and accessibility targets" and forbids an invented score. Those two requirements pull against each other, because the number everyone expects — a Lighthouse performance score — cannot be produced honestly here. A score is a weighted blend of paint and blocking timings, and every one of those moves with CPU contention, thermal state, and whether the browser is headless. Run on a developer laptop next to a six-minute test matrix, the same commit scores differently from itself. Publishing one number as *the* score would be the invented score the objective rules out, whatever tool produced it.

The objective's `allowedPaths` sharpen the problem. They exclude `package.json`, `playwright.config.ts`, `vitest.config.ts` and `.github/**`, so this objective may add no dependency, no npm script, and no CI job. Whatever it measures, GitHub Actions will not run it. `npx lighthouse` would resolve at run time, download roughly 40 MB per invocation, and add an undeclared dependency to a repository whose whole gate story is reproducibility.

There is a second, quieter problem. Every existing end-to-end gate in this repository runs against `next dev`: `playwright.config.ts` sets `webServer.command` to `npm run dev`, and the repo is invested in that — `next.config.ts` carries `allowedDevOrigins` for it, `scripts/verify.mjs` restores the `next-env.d.ts` that `next dev` rewrites, and `e2e/a11y.spec.ts` skips the development overlay by tag. So the suite measures an unminified bundle with React in development mode, and has never measured what a visitor would receive.

## Decision

- **Two artefacts, not one, and they are different kinds of claim.** Byte counts are gated; timings are reported. A number that cannot be reproduced on another machine does not get to fail a build.
- **`scripts/check-bundle-budget.mjs` is the gate.** It reads the prerendered HTML from the production build, resolves the chunks that HTML references — never a hardcoded name, because turbopack rehashes every build — gzips them, and exits non-zero when the initial JavaScript and CSS exceed the budget. It also asserts that no chunk in the initial payload contains `THREE.WebGLRenderer`, which turns "the globe is lazy" from a true statement into a guarded one. The budget is a single named constant with its rationale beside it, set with enough headroom that ordinary dependency drift does not turn it red for a reason unrelated to what it guards: a gate that fails for the wrong reason gets raised rather than obeyed, and then it guards nothing. It is sized to stop a chunk of consequence re-entering the first load, not to police a few kilobytes. These numbers are exact, need no browser, and are identical on every machine, which is what earns them a place in the matrix.
- **It runs in `FULL_VERIFICATION_COMMANDS`, after `npm run build`.** That file is `scripts/lib/verification-plan.mjs`, shared by `npm run verify` and `scripts/ship-pr.mjs`, so every future objective inherits the budget. It is the only automation seam inside this objective's allowed paths, so the budget is enforced at ship time by the local matrix rather than by GitHub. That is weaker than a CI job, and a contributor who never runs the matrix will not see it fail.
- **`scripts/measure-perf.mjs` is the report, and it is run by hand.** It drives the Playwright chromium the repository already installs, over the DevTools protocol, against a real `next build && next start`. No dependency is added and no score is computed. Its output is a JSON report stamped with commit SHA, branch, a tree-dirty flag, and **machine class** — platform, architecture, CPU model and count, memory, and the Node, Playwright, chromium and Next versions. Machine class, deliberately, and not hostname: a hostname identifies a person, this report is committed, and `.claude/rules/security.md` forbids user-specific identifiers in the repository. What a reader needs in order to judge whether two runs are comparable is the class of machine, not whose it was. The report states in its own text which numbers are comparable and which are not: byte counts and request counts are exact; paint and blocking timings are reported as **before-and-after deltas measured back to back on one machine in one session**, never as absolutes.
- **One machine, one session, one operator.** The lead runs it. Two agents on two machines produce two incomparable reports, and a report whose provenance is mixed is worse than no report.
- **The variance is measured, published, and not a story.** Every profile is run three times and the report publishes min, median, max and the individual runs. Nothing is averaged — an average of three timings on a contended host describes no run that happened. The spread is the precision, and it is in `docs/perf/production-baseline.json`, not here. Publishing n=1 and then choosing *which* n=1 would be this document arguing that a single timing cannot be trusted and then asking to be trusted about a single timing. Two things the runs show and the shape of the report encodes: the unthrottled desktop profile is the volatile one — its spread has itself differed by an order of magnitude between sessions of the same bundle, so a desktop paint figure is not quotable even as a range — while the CPU-throttled profile stays tight, because throttling swamps host variance. That is why Lighthouse throttles. And `navigation.responseStart` is not reported as time-to-first-byte at all, because Chrome charges emulated latency to the body transfer rather than to the response start: `responseStart` is effectively identical under both profiles while `responseEnd` goes from low single-digit milliseconds to most of the emulated round trip, so the report prints only `responseEnd` and labels it as such. A low single-digit time-to-first-byte printed beside a throttled profile would have read as fabricated.
- **The report is generated, never typed.** A hand-written table of numbers is indistinguishable from a fabricated one after the fact. "Reports committed or linked" is satisfied only by an artefact a single command regenerates.
- **Accessibility is gated by a test that computes in the page, and the gate has a stated blind spot.** `e2e/contrast.spec.ts` walks the rendered dashboard, reads computed styles, composites the actual stacked backgrounds including alpha, and applies the WCAG 2.2 relative-luminance ratio against 4.5:1 — relaxing to 3:1 only where the computed font size and weight earn it, read off the element rather than assumed. What it cannot do is read the canvas: text over the globe is scored against the frame behind the canvas, not the pixels actually painted under it, and the test says so in its own failure output. That text was measured out of band instead, by `scripts/measure-ink-contrast.mjs`, which samples the painted pixel under the glyph strokes across six globe states and writes `docs/a11y/ink-contrast.json`. It gates nothing, so a future palette change or a denser starfield can move those numbers without the matrix noticing — which is exactly why it is a committed artefact one command regenerates rather than a figure typed into a comment. The same standard this ADR sets for the performance report, applied to the measurement that was previously the only unfalsifiable number in the objective. It deliberately does not recompute the audit's arithmetic from token values: the glass gradients and the body radial gradients lighten the composited background slightly, always in the same direction, and several call sites sit within a few hundredths of the threshold. A test seeded with hand-computed ratios would be a test of the arithmetic that produced them.
- **Any axe-core pass is discovery only and never enters the merge gate.** It cannot be a declared dependency under these allowed paths, so it cannot be something the build depends on. It is a way to find findings; the findings are then encoded as tests that stand on their own. If the transitive package ever disappears, no gate breaks, because no gate ever depended on it.
- **Preloading the globe textures was considered and deliberately not done.** The three textures are 667 KB of the 1.45 MB a first visit transfers, and a `<link rel="preload" as="image">` in the layout would start them earlier. It would also start 667 KB downloading at first paint for every visitor, competing with the initial payload this objective just spent its effort shrinking, and the element it would help is the one behind a deliberate lazy boundary. Whether that trade is net positive is a question about unthrottled paint timing — the one number this ADR's own evidence says is too unstable to decide anything with. There is no measurement available that could settle it, so making the change would be acting on a hunch in an objective whose whole point is not to. It is left undone and recorded.
- **The dev-versus-production split is stated, not hidden.** The report says which numbers came from a production build and which existing gates remain development-measured. Converting the whole suite would cost a production build per run and buy little.

## What this got wrong first

The gates in this ADR were not designed correctly and then implemented. Each was wrong in a way that would have left it passing while measuring nothing, and each was found by attacking it rather than by reading it. Squash-merge deletes the commit bodies, so the list lives here:

- **The three.js assertion was a string search with no positive control.** A `three` release renaming `THREE.WebGLRenderer` would have disarmed it silently, forever. It now fails if the marker appears in no built chunk at all.
- **The byte budget had no floor.** A ceiling is satisfied by measuring nothing: zero bytes passed, and twenty-four bytes passed.
- **The planner could hoist the budget ahead of the build.** `unique()` keeps the first occurrence, so any objective naming the check in its own `verify` array would have measured a stale `.next` — a green gate over the previous objective's build.
- **The report's `treeDirty` flag was always true**, because the report is written into the tree it describes, and it took three fixes to stop being always true. The first missed git collapsing a new directory to `?? docs/perf/`; the second read NUL-separated paths; the third found that the shared `git()` helper trimmed every command's output, which eats the leading space of an unstaged modification's ` M path` record and shifts the fixed-offset path slice by one character, so no path ever matched its own exclusion. Each fix was believed because the flag was only ever observed in the state where true was plausible. It is now checked in both directions — dirty with a stray file present, clean without one — because a flag only ever seen reading true has not been observed to work. A residual remains: the second record of a rename is a bare path and is mangled by the same slice, forcing the flag true. That one is left, but "it fails safe" is what was said about the other three.
- **The load average was sampled once, before the profiles ran**, so the field could not observe mid-run contention, which is the only case it was added for.
- **The contrast comment claimed measurements taken against a palette that had been replaced two commits earlier**, and twice attributed near-1:1 readings to defects that were artifacts of the instrument — a bounding box measures the background between letters, and an element rect measures decorative children.
- **The console summary rounded cumulative layout shift to a whole number.** A real 0.0314 desktop shift printed as `0` while the committed JSON beside it held the true value. Rounding is not neutral: this one was wrong in the reassuring direction, on the metric a reader is least likely to go and check.
- **This ADR restated its own report's timings, and they drifted.** Six figures were written into the prose above as evidence for the argument that single timings cannot be trusted; the next regeneration on the same machine contradicted every one of them, including the factor-of-three variance claim, which came back at a factor of 1.07. The figures were deleted rather than corrected, because correcting them only resets the clock. Prose here now argues from the shape of the numbers and points at the artifact for the numbers themselves.

The pattern is one defect wearing six hats: a check that cannot fail is worse than no check, because it is trusted. Anything added to this matrix should be mutated and observed failing before it is believed.

## Consequences

Positive: every number this objective publishes can be regenerated by one command, and the one number that fails a build — bytes — is exact and machine-independent. The three.js assertion converts an existing property into a guarded one, so the lazy import cannot be removed silently. The contrast test measures the page rather than a model of the page, so it stays correct if a background changes.

Negative: the budget is enforced only where the local matrix runs, because this objective may not add a CI job; a contributor who never runs `npm run verify` will not see it fail, and closing that gap needs a later objective with `.github/**` in scope. The timing report is a point-in-time measurement by one operator on one machine, so it evidences a direction of travel and not a target anybody else can reproduce exactly. And there is no single headline score to put in a README — deliberately, because the honest alternative to an unreproducible score is not a better score but a smaller claim.
